# Vector sidecar for remote logs

**Type**: AFK

## Parent

`specs/operator-mvp/PRD.md` — chart parity. The `memgraph-high-availability` chart's `vectorRemote` block, the logs half of the remote monitoring `27-vmagent-remote-write.md` brought the metrics half of; scoped on 2026-10-01.

## What to build

`spec.monitoring.vectorRemote`, the chart's block under the chart's name, beside `vmagentRemote`: a Vector sidecar in every pod of both roles that reads the instance's own log stream from Memgraph's monitoring websocket and pushes it to a Loki-compatible endpoint. It is how Memgraph reads a customer cluster's logs: Memgraph cannot reach into the customer's network, so the cluster pushes, outbound only, to the VictoriaLogs Memgraph runs, at the endpoint and with the credentials Memgraph hands the customer; any Loki works the same way. Presence-based like every other block, with `logsEndpoint` the one required field — a base URL Vector appends `/loki/api/v1/push` to, so VictoriaLogs takes its `/insert` path.

The source needs nothing from the operator. Memgraph starts the monitoring websocket on every instance, both roles, at `--monitoring-port` 7444 with no switch to turn it off, and streams each log line as it is written; the sidecar dials it on the loopback address, so no Service, no port and no API access are involved and the Memgraph container is untouched. The websocket shares the Bolt TLS context, so on a cluster with `spec.tls.bolt` the sidecar dials `wss` with TLS switched on explicitly — Vector does not infer it from the scheme, as the smoke test against the pinned image showed — and without verifying a certificate that names no loopback address, for the reason the operator's own dials do not. Vector retries a refused connection on its own, so the sidecar may start before Memgraph listens.

One ConfigMap `<cluster>-vector-config` serves both roles, carrying the monitoring marker and pruned by it: everything that differs per pod reaches Vector through the environment — the role, the pod and namespace names from the downward API, the credentials by Secret reference — and Vector interpolates `${VAR}` into its configuration when it loads it. The configuration is marshalled from a typed struct, not templated text. Its remap is the chart's in spirit: Memgraph frames each line as `{"event": "log", "level": ..., "message": ...}` but escapes only quotes and newlines, so a frame that is not valid JSON is kept whole with `level=unknown` rather than dropped, and Memgraph's `warning` and `critical` become `warn` and `fatal`. The Loki sink carries the chart's labels — `app` and `job` `memgraph`, `role`, `namespace`, `pod`, `level` — plus `extraLabels` as written, with the operator's keys winning a collision, so the dashboards Memgraph keeps for chart users work for operator users unchanged. The sink's health check is off, because a gateway in front of VictoriaLogs need not answer Loki's ready endpoint.

The sidecar lands after the uploader and before the user containers on both roles, runs under the pod's identity and the restricted security context every operator container runs under, keeps its state on an emptyDir because its root filesystem is read-only, and carries no probe: a sidecar's readiness must never gate the pod's, which is what registration waits on. Adding or removing the block is a pod-template change the roll carries. Nothing lands in status.

Four things the chart has are deliberately absent. `enabled`, for the reason every block lacks it. `data` and `coordinators`, the per-role switches: the sidecar runs on both roles, because a coordinator's log is where a failover decision is explained. `websocketPort`: the sidecar dials Memgraph's default and the operator leaves it alone. And the `grafanaDashboard` ConfigMap for the "Memgraph Logs" dashboard: the logs go to the Grafana on Memgraph's side, which is where the dashboard lives, and it needs a VictoriaLogs datasource plus the `cluster_id`-labelled metrics the vmagent ships, neither of which a customer's Grafana has.

The controller gains one line: `desiredMonitoring` appends the ConfigMap. No new RBAC, no new kinds. The shared basic-auth Secret type is renamed from the vmagent's `RemoteWriteBasicAuthSpec` to `BasicAuthSecretSpec` now that two blocks use it.

Testing follows the house split. Builder tests pin the configuration text with every knob, without auth and with Bolt TLS, the sidecar on both roles after Memgraph and before a user container with each role's own `ROLE`, the two volumes, and a cluster without the block carrying none of it. Envtest covers creation with the CRD default landing, both StatefulSets carrying the sidecar, and removal pruning the ConfigMap and the sidecar from the templates; the validation suite covers the required endpoint, its pattern, the required Secret name and the label-name rule. The e2e deploys a single-node VictoriaLogs in the cluster's namespace, adds the block with a basic-auth Secret and an extra label, watches the roll carry the sidecar into every pod one at a time, asserts every declared pod's lines are queryable at the sink by LogsQL, then removes the block and watches the roll take the sidecar out and the ConfigMap go. Before any of it, a Docker smoke test ran the pinned Vector against a real Memgraph and VictoriaLogs, plaintext and `wss`.

## Acceptance criteria

- [ ] `spec.monitoring.vectorRemote` is an optional struct with `logsEndpoint` (required, `^https?://`), `auth.secretName`, `extraLabels` (keys CEL-checked as label names), `image.{repository,tag,pullPolicy}` (defaults `docker.io/timberio/vector`, `0.49.0-debian`, `IfNotPresent`) and `resources`; no `enabled`, per-role switches, `websocketPort`, `namespace` or `grafanaDashboard`
- [ ] Present, both roles' pod templates carry a `vector` container after Memgraph and the uploader and before user containers, with `ROLE`, `POD_NAME`, `POD_NAMESPACE` and, with `auth`, `LOGS_USERNAME`/`LOGS_PASSWORD` by Secret reference, the configuration mounted read-only and an emptyDir for state, under the restricted security context and with no probe; builder tests pin both roles
- [ ] One ConfigMap `<cluster>-vector-config` with the monitoring marker and a controller owner reference holds `vector.yaml`: websocket source on `ws://127.0.0.1:7444` (`wss` with `tls.enabled` and verification off under `spec.tls.bolt`), the remap, and a Loki sink at the endpoint with the chart's labels plus `extraLabels`, basic auth from the environment when named, health check off; builder tests pin the text in all three variants
- [ ] Removing the block prunes the ConfigMap and the sidecar leaves both templates; envtest covers creation and removal
- [ ] Admission rejects a block without `logsEndpoint`, an endpoint without an http scheme, an `auth` without `secretName`, and an `extraLabels` key that is not a label name; the validation suite covers each
- [ ] `make manifests generate chart-sync` regenerated, `make chart-verify` green, the CRD's compact JSON stays under the 256KB client-side apply limit
- [ ] E2E: with a single-node VictoriaLogs deployed by the test, adding the block rolls the sidecar into every pod one at a time, every declared pod's lines carrying `cluster_id` are queryable at the sink, and removing the block rolls the sidecar out and prunes the ConfigMap
- [ ] `docs/monitoring.md` documents the block, the always-on websocket, the derived `wss`, the chart's labels, the credentials, the roll, and why the per-role switches, `websocketPort` and the logs dashboard are absent; the sample, the README and `CLAUDE.md` describe it
