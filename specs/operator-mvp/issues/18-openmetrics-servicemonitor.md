# OpenMetrics endpoint and ServiceMonitor

**Type**: AFK

## Parent

`specs/operator-mvp/PRD.md` — monitoring was listed there as a later version; this issue and `19-grafana-dashboard.md` are that version, scoped in a design interview on 2026-09-25.

## What to build

Make the metrics endpoint every Memgraph instance already serves a stated part of the operator's contract, and let a cluster ask for the one object a Prometheus Operator needs to scrape it. Nothing else the HA chart offers around monitoring comes along: no `mg-exporter`, no vmagent, no Vector sidecar, no JSON format. OpenMetrics only.

The endpoint itself needs no switch. Memgraph's enterprise build starts the metrics HTTP server unconditionally, on both roles, at `--metrics-address=0.0.0.0` and `--metrics-port=9091`; from 3.13 the format defaults to OpenMetrics and JSON is deprecated. So the operator cannot turn the endpoint off and should not pretend to. What it does unconditionally, with no spec involved, is declare it: a `metrics` container port on 9091 on both roles, a `metrics` port on both headless Services, and `--metrics-format=OpenMetrics` in the common args of both roles. The pin is deliberate even though the default image already defaults to it — it makes the format something the operator states rather than something the image tag happens to ship, and it protects a user on a 3.11 or 3.12 image where JSON is still the default. The consequence is that a user who runs their own Prometheus Operator, or a plain Prometheus with Kubernetes service discovery, gets a scrapeable cluster with an empty spec. That is the point: many users already have their own ServiceMonitors, PodMonitors or scrape configs, and the operator must not stand in their way.

For the users who want the operator to hand Prometheus Operator the object, `spec.monitoring.serviceMonitor` is an optional struct whose presence creates one `ServiceMonitor` in the cluster's namespace and whose removal prunes it, the way `externalAccess` works and for the same reason: `enabled: false` beside a configured block is a state nobody wants and the prune logic is simpler with one signal. The block is called `monitoring` rather than the chart's `prometheus` because nothing in it is Prometheus-specific except the ServiceMonitor kind itself. One ServiceMonitor covers the whole cluster. It selects both headless Services by the cluster's identity labels (`app.kubernetes.io/name=memgraph`, `app.kubernetes.io/instance=<cluster>`) with one endpoint on port `metrics`, path `/metrics`, scheme `http`; the external Services carry the same labels but no `metrics` port, so they yield no targets, which is what makes selecting on the cluster's labels safe. Scraping through the headless Services, which publish not-ready addresses, means a recovering pod is scraped and fails, which is the `up=0` a monitoring stack wants to see rather than a target that vanishes.

The knobs are `labels`, `annotations` and `interval`. `labels` is what the user's Prometheus selects ServiceMonitors by — the documented example is `release: kube-prometheus-stack` — and replaces the chart's `kubePrometheusStackReleaseName`, which hardwires one distribution. `interval` is optional and, omitted, is omitted from the object too, so Prometheus's global default applies and the operator invents no number. Three knobs the chart has are deliberately absent. `namespace`: owner references cannot cross namespaces, and the operator garbage-collects and prunes through them, so a ServiceMonitor in another namespace would leak on removal and need cluster-wide list and delete rights to find; Prometheus Operator solved this from its side with `serviceMonitorNamespaceSelector`, and the docs say so. `scheme` and `tlsConfig`: they only mean something once Memgraph serves metrics over HTTPS, which the operator has no support for yet; they arrive with TLS, driven by the same spec that turns it on.

`ServiceMonitor` is a CRD from `monitoring.coreos.com/v1` and the operator never bundles it. The treatment is exactly the Gateway API's: `cmd/main.go` discovers once at start whether the kind is served at `v1`, the controller owns and lists it only if so, and a cluster asking for `serviceMonitor` without it gets `Converged=False/ApplyFailed` with a message naming the missing kind and what installs it, while the rest of the cluster reconciles as before. Installing the CRD later takes an operator restart, documented rather than detected, as for Gateway. The softer alternative — skip the object with a warning event — hides a configuration mistake behind a green condition, which is what a GitOps gate would miss.

The object is built by the typed API from the `github.com/prometheus-operator/prometheus-operator/pkg/apis/monitoring` module, pinned to the newest release on the project's Kubernetes minor line so the dependency costs no Kubernetes bump. The module ships no CRD manifest, so one copy of the ServiceMonitor CRD YAML at that same version lives under `test/crds/`: envtest loads it beside the Gateway API CRDs, and a `hack/kind-prometheus-crds.sh` applies the same file to the Kind cluster from `make setup-test-e2e`, so there is one copy to bump. The prune path generalises `pruneExternalKind` to take the marker selector it lists by; the monitoring objects carry their own marker label so an external-access change never touches them and vice versa. A new `+kubebuilder:rbac` marker grants `servicemonitors` in `monitoring.coreos.com` the same verbs the Gateway kinds get, granted whether or not the cluster serves the group, and `make chart-sync` carries it into the install chart.

Testing follows the house split. Builder tests pin the two ports and the arg, and a golden test pins the ServiceMonitor's shape with every knob set. Envtest covers creation on a spec with the block, pruning when the block is removed, and the `ApplyFailed` condition on a reconciler told the kind is not served. The e2e suite proves two things without running a Prometheus, because whether Prometheus discovers and scrapes a ServiceMonitor is Prometheus Operator's contract, not this one's: that a coordinator pod and a data pod on the licensed image answer on 9091 with OpenMetrics text, and that a cluster with the block gets a ServiceMonitor selecting both headless Services on port `metrics` which disappears when the block is removed.

No clusters run on the operator yet, so the pod-template change the port and the arg cause is free; on a running cluster it would have meant one sequenced roll, which is the correct outcome and needs no special handling. Nothing new lands in status: nothing here is discovered.

## Acceptance criteria

- [ ] Both roles' containers declare a `metrics` port on 9091 and both headless Services publish it; builder tests cover both
- [ ] Both roles' common args carry `--metrics-format=OpenMetrics`; builder tests cover it
- [ ] `spec.monitoring.serviceMonitor` is an optional struct with `labels`, `annotations` and `interval`; no `enabled`, no `namespace`
- [ ] Present, one ServiceMonitor named after the cluster is created in the cluster's namespace, selecting both headless Services by the cluster's identity labels, with one endpoint on port `metrics`, path `/metrics`, scheme `http`, and `interval` only when set; golden test pins the shape
- [ ] The ServiceMonitor carries a controller owner reference and the monitoring marker label; removing the block deletes it on the next pass, and external objects are untouched by either
- [ ] `cmd/main.go` discovers whether `ServiceMonitor.monitoring.coreos.com` is served at `v1`; the kind is owned and listed only when it is
- [ ] A cluster with the block on a reconciler told the kind is not served reports `Converged=False/ApplyFailed` naming the missing kind, and still reconciles everything else; envtest covers it
- [ ] The prometheus-operator API module is pinned to a release on the project's Kubernetes minor line, and `test/crds/` carries the ServiceMonitor CRD of that same version, loaded by envtest and applied by `hack/kind-prometheus-crds.sh`
- [ ] A `servicemonitors` RBAC marker with get/list/watch/create/patch/delete is added; `make manifests generate chart-sync` regenerated and `make chart-verify` green
- [ ] E2E: a coordinator and a data pod answer on 9091 with OpenMetrics text; a cluster with the block gets the ServiceMonitor, and removing the block prunes it
- [ ] `docs/monitoring.md` states the contract: what is unconditional, what the block creates, the missing-CRD behaviour, why there is no `namespace`, and how to point a Prometheus in another namespace at it; the README links to it
