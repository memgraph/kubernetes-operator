# vmagent remote write

**Type**: AFK

## Parent

`specs/operator-mvp/PRD.md` — chart parity. The `memgraph-high-availability` chart's `vmagentRemote` block, which issue 18 left out of the monitoring version; brought back in and scoped on 2026-10-01.

## What to build

`spec.monitoring.vmagentRemote`, the chart's block under the chart's name, beside `serviceMonitor` and `grafanaDashboard`: one vmagent the operator runs in the cluster's namespace that scrapes every instance's OpenMetrics endpoint and remote-writes the samples to a Prometheus remote-write endpoint. It is how Memgraph monitors a customer's cluster, which the two existing blocks cannot do: Memgraph cannot reach into the customer's network to scrape, so the cluster pushes its metrics, outbound only, to the VictoriaMetrics Memgraph runs, at a URL and with credentials Memgraph hands the customer. Any Prometheus remote-write endpoint works the same way. Presence-based like every other block: present, the vmagent runs; removed, it is pruned through the monitoring marker issue 18 built. `remoteWrite.url` is the one required field.

The operator creates two objects. A Deployment `<cluster>-vmagent`, one replica, under the restricted security context every container it builds runs under, as uid 65534 because the vmagent image is built from scratch and names no user, with no ServiceAccount token because it needs nothing from the API server, buffering unsent samples on an emptyDir since its root filesystem is read-only. And a ConfigMap `<cluster>-vmagent-config` holding the scrape configuration, rendered by marshalling a typed struct rather than templating text: one job `memgraph` with a static target per pod the operator runs, by pod DNS on the metrics port, at the applied counts the external objects already follow — static targets rather than discovery, as in the chart, because the operator knows the topology and vmagent then needs no RBAC. `scrapeInterval` (default the chart's `15s`) and `externalLabels` go under `global`; the keys of `externalLabels` are checked by CEL to be Prometheus label names, because an invalid one would otherwise only fail inside vmagent at runtime. The scheme follows `spec.tls.bolt` the way the ServiceMonitor's does. vmagent re-reads the file on an interval, so a scale changes the ConfigMap and nothing else: no restart, no loss of the buffer. The url, the image and the credentials Secret are pod-template fields the Deployment rolls itself.

Credentials come by reference and never touch the operator: `remoteWrite.basicAuth.secretName` names a Secret with the keys `username` and `password`, the `kubernetes.io/basic-auth` keys and what the chart's `usernameKey` and `passwordKey` default to; here they are fixed, as the TLS Secrets' keys are. The password is mounted read-only and vmagent reads it through its `passwordFile` flag, re-reading it every second, so rotation needs no restart and the password is never on the command line, where the chart's `$(MONITORING_PASSWORD)` puts it; the username, not the secret part, reaches vmagent through an environment variable from the same Secret (the pinned vmagent has no `usernameFile` flag). The operator keeps holding no Secret permissions.

Four things the chart has are deliberately absent. `enabled` and `namespace`, for the reasons every block lacks them. `httpPort`: vmagent listens on 8429 inside the pod and nothing outside dials it. And the whole `kubernetes` branch — kube-state-metrics, node-exporter and the kubelet through the API server's node proxy — because those targets are not this cluster's, and the kubelet job needs a ServiceAccount bound to a cluster-scoped ClusterRole on `nodes`, `nodes/proxy` and `pods`, which the operator would have to hold itself to grant and which no owner reference garbage-collects when the cluster goes. Infrastructure metrics are a cluster-wide agent's job, documented as such.

The controller gains little: `desiredMonitoring` takes the replica counts and appends the two objects, `pruneMonitoring` lists Deployments too, a `deployments` RBAC marker with the pruned kinds' verbs, `Owns(Deployment)`, and a label-scoped Deployment informer in `main.go` like the ConfigMap one, because every namespace has Deployments that are none of the operator's business. Nothing lands in status: whether the endpoint accepts the writes is vmagent's to report.

Testing follows the house split. Builder tests pin the Deployment with every knob and with the defaults alone, the scrape config text at given counts, the https variant and the marker. Envtest covers creation with the CRD defaults landing, the targets following the counts, and pruning the block alone while the sibling ServiceMonitor stays; the validation suite covers the required url, the url pattern, the required Secret name and the label-name rule. The e2e deploys a single-node VictoriaMetrics in the cluster's namespace — the first real sink in the suite, because "the samples arrive" is the whole feature — gives the block its URL and a basic-auth Secret, and asserts every declared instance's `up` series is queryable there carrying the external label, under the restricted Pod Security Standard the namespace enforces; then removes the block and asserts the Deployment and ConfigMap are gone.

## Acceptance criteria

- [ ] `spec.monitoring.vmagentRemote` is an optional struct with `image.{repository,tag,pullPolicy}` (defaults `docker.io/victoriametrics/vmagent`, `v1.139.0`, `IfNotPresent`), `remoteWrite.url` (required, `^https?://`), `remoteWrite.basicAuth.secretName`, `scrapeInterval` (default `15s`), `externalLabels` (keys CEL-checked as Prometheus label names) and `resources`; no `enabled`, `namespace`, `httpPort`, key-name knobs or `kubernetes` block
- [ ] Present, a Deployment `<cluster>-vmagent` and a ConfigMap `<cluster>-vmagent-config` are created in the cluster's namespace with the monitoring marker and a controller owner reference; builder tests pin both with every knob and with the defaults alone
- [ ] The scrape config is one job `memgraph` with static pod-DNS targets on 9091 at the applied counts, `scrapeInterval` and `externalLabels` under `global`, `https` with `insecure_skip_verify` on a cluster with `spec.tls.bolt`; builder tests pin the text
- [ ] The vmagent runs as uid 65534 under the restricted security context with no ServiceAccount token, mounts the config read-only and re-reads it on an interval, buffers on an emptyDir, and with `basicAuth` takes the username from the Secret through the environment and reads the password from a read-only mounted file, never on the command line
- [ ] Removing the block prunes both objects and leaves a sibling `serviceMonitor` alone; envtest covers creation with defaults landing and the prune
- [ ] Admission rejects a block without `remoteWrite.url`, a url without an http scheme, a `basicAuth` without `secretName`, and an `externalLabels` key that is not a label name; the validation suite covers each
- [ ] Deployments are granted get/list/watch/create/patch/delete, owned, label-scoped in the manager cache and listed by `pruneMonitoring`; `make manifests generate chart-sync` regenerated, `make chart-verify` green, the CRD's compact JSON stays under the 256KB client-side apply limit
- [ ] E2E: with a single-node VictoriaMetrics deployed by the test, every declared instance's `up{job="memgraph"}` series carrying the external label is queryable at the sink under the restricted policy, and removing the block prunes the Deployment and the ConfigMap
- [ ] `docs/monitoring.md` documents the block, the fixed Secret keys with the `kubectl create secret` line, the derived scheme, the no-restart config reload, and why `namespace`, `httpPort` and the `kubernetes` branch are absent; the sample, the README, the chart README and `CLAUDE.md` describe it
