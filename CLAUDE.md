# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A kubebuilder-based Go operator for Memgraph high-availability clusters. It exposes one CRD, `MemgraphCluster` (group `memgraph.com`, version `v1alpha1`, short name `mgc`), and replaces the `memgraph-high-availability` Helm chart's fire-and-forget registration Job with continuous, state-aware reconciliation over Bolt.

The repository was reset for this effort (prior attempt is on `archive/pre-operator-mvp`). Work is driven by `specs/operator-mvp/PRD.md` and sliced into PR-gated issues in `specs/operator-mvp/issues/` — read the PRD before making design decisions; it records what is in scope (provision, bootstrap, observe) and what is deliberately out (day-2 ops, scaling, TLS, external access, monitoring).

`AGENTS.md` contains the generic kubebuilder agent guide (scaffolding commands, marker reference, never-edit rules). Follow it, especially: never hand-edit `config/crd/bases/*`, `config/rbac/role.yaml`, `zz_generated.*.go`, or `PROJECT`; never delete `// +kubebuilder:scaffold:*` markers.

Run a single test (Ginkgo suites):

```sh

```

Envtest packages need `KUBEBUILDER_ASSETS`; outside of `make test` set it with:
`KUBEBUILDER_ASSETS=$(bin/setup-envtest use <k8s-version> --bin-dir bin -p path)`

CI (`.github/workflows/`) runs `make lint-config`, `make lint`, `make test-unit`, `make test`, `make chart-verify`, `make helm-lint`, `make chart-version-check`, `make test-chart-publish`, `make test-chart`, and `make test-e2e` on every PR — all must be green. ### Toolchain quirks (do not "fix" these)

- Coverage is opt-in (`make test COVER_FLAGS="-coverprofile cover.out"`). Plain `go test -cover` breaks under Go toolchain auto-switching (covdata tool build fails), so `make test` must stay coverage-free by default.
- The golangci-lint Makefile install pins `GOTOOLCHAIN` to the project's Go version; `go install` otherwise builds it with an older toolchain that refuses to lint this project.

## Architecture

The PRD defines seven modules with two pure cores and one mock seam; an eighth (the rolling-restart decision) was added post-v1 as a third pure core. Keep this separation — it's what makes the logic testable without a cluster:

1. **API types** (`api/v1alpha1/`) — spec/status with kubebuilder + CEL markers. Replica counts (coordinators, data instances) are **mutable in both directions**, bounded by schema floors alone (coordinators ≥ 3 and odd, data instances ≥ 1) — enforced by the CRD, not a webhook. Defaults are declared as CRD schema defaults *and* mirrored as Go constants in `memgraphcluster_types.go` so resource builders behave correctly on specs that never passed admission (unit tests).
2. **Resource builders** — pure functions: spec in, desired Kubernetes objects out (one StatefulSet per role + headless Services; per-pod identity such as coordinator ID and advertised addresses derived from pod ordinals). No API calls, no side effects. Tested golden-style.
3. **Memgraph HA client** — a narrow Go interface (show instances, show replication lag, register instance, add coordinator, set main, demote/unregister instance, remove coordinator, yield leadership) over the Bolt driver. Everything above depends on the interface, never the driver — this is the mock seam.
4. **Registration planner** — pure diff: declared topology + observed `SHOW INSTANCES` in, ordered registration commands out (empty when converged). Reconciliation semantics live here: read-before-write, idempotent, re-issue only missing registrations. A MAIN is promoted only when the cluster has none — at bootstrap, and after the planner itself demoted a data instance that is retiring; a MAIN that is staying is never overridden, because failover belongs to the Raft coordinators. A lowered count is the one removal the planner drives: `DEMOTE INSTANCE` the retiring MAIN, promote a survivor, `UNREGISTER INSTANCE` the retiring data instances, `REMOVE COORDINATOR` the retiring coordinators, and only then does the controller shed their pods (see `specs/operator-mvp/issues/15`, `16`). Moving MAIN off a retiring instance is the one step that can lose data, so it has a precondition nothing else does: a survivor that is both reachable and reported by `SHOW REPLICATION LAG` as holding every transaction the MAIN committed, in every database. Without one, the demotion, the promotion and that instance's unregistration are all left out of the plan and the retiring MAIN keeps serving — a scale-down that pauses, not one that drops writes. Because that state plans *nothing*, an empty plan is not proof a retirement finished: `planner.Retired` is what gates shedding the pods. One command breaks the pure-diff mould: `YIELD LEADERSHIP`, needed because Raft refuses to remove its own leader. It names no successor, so it is always a plan's **last** command and terminal — the controller requeues and re-observes under whichever coordinator won the election. The one mutable thing about a registration is the announced `bolt_server`: the declared topology carries the external address of every exposed member (see external access below) and the planner issues `UPDATE CONFIG FOR INSTANCE|COORDINATOR` whenever the observed one differs, skipping an empty observed address (a view that does not report one) and every retiring member.
5. **Controller** (`internal/controller/`) — fetch CR, server-side-apply builder output, gate on pod readiness, run planner against the HA client, write status/conditions.
6. **Operator install chart** (`charts/memgraph-operator/`) — lives in this repo, cross-published to `memgraph.github.io/helm-charts` at release. Its `crds/` and `rbac/manager-rules.yaml` are **generated** (`make chart-sync`, verified by `make chart-verify`): the manager's ClusterRole comes from the `+kubebuilder:rbac` markers, so tightening or widening the controller's permissions means editing the markers, never the chart. The e2e suite installs the operator through this chart, so every scenario runs under the RBAC users get. The chart's `version` and its `appVersion` (the operator image tag) move **independently**: tag `v<version>` releases the operator, `chart-<version>` releases the chart alone — see `docs/releasing.md`.
7. **Rolling-restart decision** (`internal/rollout/`) — the third pure core: both roles' pods reduced to `{name, revisionHash, ready}` plus each StatefulSet's `UpdateRevision`, the `SHOW INSTANCES` view and `SHOW REPLICATION LAG` in, **exactly one** action out (`Done` / `Wait(reason)` / `Delete(pod)`). Both StatefulSets use `updateStrategy: OnDelete`, so the operator owns every pod restart and this decides which pod is next: data instances before coordinators, the observed MAIN last of its role, the Raft leader last of its. Nothing is persisted — pods already carrying the new revision *are* the ones already restarted, so a mid-roll spec revert or a Raft-driven MAIN move self-corrects. One action per pass and never a list, because every step re-gates on fresh lag. It issues no Bolt commands at all; a roll is invisible to the planner. A role is judged only when its StatefulSet's status describes the template it carries (`status.observedGeneration == metadata.generation`, and the generation is at least the one this pass's apply returned): both StatefulSets are applied in one pass but their statuses land one at a time, and a data StatefulSet still showing its old revision makes the data plane look done and sends a coordinator first — the e2e caught exactly that.
8. **E2E harness** (`test/e2e/`, build tag `e2e`) — multi-node KinD with real Memgraph images.

Test philosophy (from the PRD): assert external behavior, never internal call ordering or private state. Builders get golden tests, planner gets pure topology-diff cases, the rolling-restart decision gets pure cases over pod revisions and observed cluster state, controller gets envtest with the HA client mocked.

## Conventions

- Spec knob names mirror the HA Helm chart's vocabulary where the concept carries over (e.g. the `secrets.name` / `secrets.licenseKey` / `secrets.organizationKey` block) — check the chart before inventing a name.
- Every optional block is presence-based and there is no `enabled` anywhere in the API (decided 2026-09-28): `externalAccess`, `monitoring.*`, `tls.*`, `scheduling.podAntiAffinity`, `sysctlInitContainer`, `fixOwnershipInitContainer`, `securityContext` and `coreDumps.<role>` are on when written and off when absent. A behavior that should be on for most users lives in the sample and the quickstart example, never in a schema default, because a schema default on a block makes it impossible to turn off by leaving it out. The one default-on toggle left is `coreDumps.configureCorePattern`, a bool inside a block that is itself presence-based.
- **Memgraph flags** (`spec.flags.<role>`, `map[string]string`, flag name without dashes to value; replaced the `extraArgs` list 2026-10-02) never travel as container args: each role's flags are rendered into a gflags flag file in a ConfigMap `<cluster>-<role>-flags` (canonical underscore spelling, sorted, the operator's logging defaults `log_level=TRACE`, `also_log_to_stderr=true`, `log_retention_days=35` as the base the map merges over) that the container loads with `--flag-file` as its **first** argument; the command line carries exactly the pinned flags admission denies in the map (ports, `bolt-address`, `monitoring-address`, `monitoring-port`, `metrics-port`, `metrics-format`, coordinator identity, `data-directory`, `log-file`, the TLS file flags) plus `aws-access-key`/`aws-secret-key` (secret material; docs say `SET DATABASE SETTING` by hand). gflags processes `--flag-file` in argument order and takes the last occurrence, so a pinned flag always wins; an unknown name inside a flag file is silently ignored, a bad value is fatal. The pod template carries `memgraph.com/flags-restart-hash` over the **startup-only** lines only, so a startup-only change rolls through `internal/rollout` unchanged and a run-time change rolls nothing. Run-time flags (the eighteen in `internal/settings`, flag name ≠ setting name, copied from `src/flags/run_time_configurable.cpp` and pinned by a test) are applied with `SET DATABASE SETTING` on **every ready pod of both roles** in the converged branch before the roll picks a pod, each pod dialed over pod DNS (`resources.DataEndpoints` joined `CoordinatorEndpoints`), read-before-write, only keys present in the file. Memgraph refuses Bolt parameters in that grammar, so values are rendered as Cypher string literals (`memgraph.cypherString`). Failures ride `Converged`: `SettingsPending` (ready pod did not answer), `SettingsRejected` (pod, command, Memgraph's error verbatim); neither fails the pass or escalates to a restart. Removing a key issues no `SET` (Andi's call until core gains a reset): a non-persisted setting reverts on the next restart, a `kRestore` one keeps its last value; a removed override of an operator default does revert, because the file then says the default.
- **Coordinator settings** (`spec.coordinatorSettings`, `map[string]SettingValue`, added 2026-10-02 at Andi's request) are the Raft-persisted cluster-wide settings (`enabled_reads_on_main`, `sync_failover_only`, `max_failover_replica_lag`, `max_replica_read_lag`, `instance_down_timeout_sec`, `instance_health_check_frequency_sec`, `global_read_only`, `deltas_batch_progress_size`): **not flags**, never in a flag file or the pod template, no restart. The controller diffs them (`settings.Diff`) against `SHOW COORDINATOR SETTINGS` over the leader connection the registration pass already holds and issues `SET COORDINATOR SETTING` once per differing key; any coordinator accepts the write and forwards it to the leader. An empty `SHOW` view means "no ready leader" and is `SettingsPending`, never a reason to write. Removing a key issues no `SET`. CEL checks the three booleans and the five numerics by shape and the key spelling; unknown keys pass through for the coordinators to refuse (`SettingsRejected`). `enabled_reads_on_main` is therefore the user's knob (the 2026-09-25 plan for the operator to own it never shipped).
- **User containers** (`spec.userContainers.<role>`, the HA chart's block) are raw `core/v1` Containers appended after the operator's own (Memgraph, then the uploader), stored schemaless like `extraVolumes` because a full Container schema per role would push the CRD past the client-side apply limit. The builder fills the restricted security context on a container that names none, so the chart's busybox example runs under PodSecurity `restricted`; a container naming its own keeps it. Name collisions and malformed entries surface as `ApplyFailed`, not at admission. **Init containers** (`spec.initContainers.<role>`, the chart's block) are the same passthrough, with the same schemaless storage and the same security context fill, appended after the operator's own init containers (`init-sysctl`, `init-core-pattern`, `init-fix-perms`) in the chart's order, so a user's runs on volumes the ownership container already fixed.
- No secret material in spec or status; secrets are consumed by reference only.
- Storage is never deleted by the operator: no finalizer-based cleanup; PVC retention (deletion *and* scale-down) maps to the StatefulSet PVC retention policy (default `Retain`). The only cluster members the operator removes are the ones a lowered replica count retires; a coordinator removed from Raft keeps running and keeps its state on purpose, which is what makes re-growing onto a retained volume safe.
- Workload pods: non-root uid 101 / gid 103 / fsGroup 103 unless `spec.securityContext` is written, in which case exactly its `runAsUser`/`runAsGroup`/`fsGroup` land and no other (an empty block leaves all three to the platform: OpenShift `restricted-v2` assigns them at admission and rejects named ones; `runAsNonRoot` and seccomp stay unconditional; not pinned, because moving the uid is what the ownership container is for), seccomp RuntimeDefault, all capabilities dropped, `terminationGracePeriodSeconds: 300` (a ceiling, not a delay — an instance killed mid-shutdown recovers from its WAL and lengthens the catch-up a roll waits on). The only privileged containers the operator builds are two init containers that write under `/proc/sys`, both on the cluster's own Memgraph image: `init-sysctl` (`spec.sysctlInitContainer`, the HA chart's block minus its image knobs and its `enabled`: presence-based, absent means off, so the sample and the quickstart example carry it) raises the node's `vm.max_map_count` to `maxMapCount` and only ever raises — the default 524288 is the floor Memgraph itself checks at startup, not the chart's 262144 — and `init-core-pattern` (`coreDumps.configureCorePattern`) sets the core pattern for a role collecting dumps. Both are node properties no namespaced sysctl can set, so a PodSecurity `restricted` namespace must leave the block out and set `configureCorePattern: false`. A third init container, `init-fix-perms` (`spec.fixOwnershipInitContainer`, the HA chart's block minus its image knobs, its `enabled` and its uid/gid knobs; presence-based with no fields, off when absent like the chart), runs last on the same image as root with `CAP_CHOWN` alone, not privileged, and chowns the lib, log and core dumps mounts to the pod's identity (`runAsUser`, and `runAsGroup` or else `fsGroup`) for storage drivers that ignore `fsGroup` (rancher.io/local-path); `restricted` rejects it too since it runs as root, and a spec-level CEL rule rejects it beside a `securityContext` that names no uid or no group, because it cannot chown to an identity the platform assigns later. Every e2e namespace enforces `restricted` (`createClusterNamespace`), so the quickstart carries none of the three and one dedicated scenario in an unlabeled namespace (`test/e2e/init_containers_test.go`) proves all of them.
- **Readiness probe only, no liveness or startup probe**, on both roles. Memgraph recovers every database inside the `DbmsHandler` constructor before any server starts, so during recovery nothing listens and no probe can tell slow from hung; a TCP liveness check could only kill a recovery that outlived a guessed budget (the HA chart's 2h), and a Bolt listener that disappears after startup means the process exited, which restarts the container anyway. A recovering pod is simply unready. The field converged on the same answer (ECK, CockroachDB, MongoDB Community run no liveness; Strimzi and cass-operator make it a process check; Percona deprecated its 7200s startup delay). Do not reintroduce them; a core health endpoint reporting recovery *progress* is the only thing that would justify a liveness check.
- StatefulSet `volumeClaimTemplates` cannot be changed, added or removed on a live cluster, and rebuilding the StatefulSet around its pods deadlocks the roll (the StatefulSet controller only recovers adopted pods in ascending ordinal order, MAIN first). Every claim-template field is therefore pinned by a CEL transition rule on the type that carries it: `storage.<role>.{libPVCSize,libStorageAccessMode,libStorageClassName,createLogStorageClaim}`, the `log*` knobs while the log claim exists, the presence of `coreDumps.<role>` (pinned on `CoreDumpsSpec`, because a rule on a block never fires for the block being added or removed whole), its `size` and `coreDumps.storageClassName` while a role collects dumps. Sizes are compared as quantities, so a unit change is not a change. The doc comment on `RoleStorageSpec` carries the argument; read it before touching any claim template knob.
- Both StatefulSets use `updateStrategy: OnDelete`, so **nothing but the operator ever restarts a workload pod**. A pod-template change no reconcile acts on takes effect never, which is what the `Updated` condition exists to report. A run-time flag change is deliberately *not* a pod-template change (see Memgraph flags above). `RollingUpdate` cannot express the required order (it sweeps highest ordinal to lowest, and `partition` is a descending cutoff, not a set), so a MAIN on any ordinal but 0 would be restarted mid-sweep and each such restart buys another failover.
- The operator never promotes a MAIN outside bootstrap and the scale-down handover: a roll deletes the MAIN's pod and lets the Raft coordinators promote. That is only safe on a Memgraph reporting an unreachable MAIN as `role=main, health=down` — a release that vacates the `main` row makes `planner.Plan` believe there is no MAIN and race the failover.
- Log messages follow Kubernetes style: capital first letter, no trailing period, past tense, object type named (see AGENTS.md for examples).
- **External access** (`spec.externalAccess`, `type: LoadBalancer | Gateway`) is operator-owned on both sides: the external objects *and* the announced `bolt_server` of every exposed member. Both modes build the same Services, one shared by the coordinators plus one per data instance (selected by the StatefulSet pod-name label); with `LoadBalancer` they are the way in, with `Gateway` they are ClusterIPs behind one operator-owned Gateway (`gatewayClassName` required, listeners `coordinators-bolt` on 7687 and `data-<n>-bolt` on `dataPortBase + n`, default 9000) fed by one TCPRoute each. The address is discovered, never declared: external-dns hostname annotation (on the Service, or in Gateway mode on the TCPRoute, then the Gateway), then the reported hostname, then the IP, pod DNS until any exists (`Converged=False/ExternalAddressPending`). `{ordinal}` in per-instance annotation values is substituted with the pod ordinal and CEL requires it on a data hostname annotation. Only the bolt address ever leaves the cluster network; the operator itself always dials coordinators on pod DNS (`resources.CoordinatorEndpoints`), never through the LoadBalancer or Gateway. External objects follow the data pods the operator *runs* (applied count), are pruned by label once the spec stops describing them, and removing the block reverts every `bolt_server` to pod DNS. The Gateway API CRDs are never bundled: `main.go` discovers once at start (`controller.GatewayAPIServed`) whether `Gateway` and `TCPRoute` are served at `v1`, watches the kinds only if so, and a cluster asking for `Gateway` without that gets `Converged=False/ApplyFailed` naming what is missing. TCPRoute is `v1` only from Gateway API v1.6 (Envoy Gateway ≥ v1.9); older releases serve it as `v1alpha2` alone and v1.6 stops serving `v1alpha2`, so no single version works on both sides — the operator requires ≥ v1.6. The e2e suite gets LoadBalancer addresses from MetalLB and a Gateway from Envoy Gateway (`hack/kind-metallb.sh`, `hack/kind-envoy-gateway.sh`, run by `make setup-test-e2e`); envtest loads the Gateway API CRDs from the `sigs.k8s.io/gateway-api` module.
- **TLS** (`spec.tls`) is presence-based per mode and takes one shared `kubernetes.io/tls` Secret per mode for both roles, fixed keys, no key-name knobs: a StatefulSet has one pod template, and Memgraph verifies no member hostname, so per-pod identities buy nothing. `bolt` (`secretName`; `tls.crt`/`tls.key` mounted read-only at `/etc/memgraph/ssl`, `--bolt-cert-file`/`--bolt-key-file`) also moves 9091 to https because Memgraph serves metrics from the Bolt server context. Everything downstream is derived, never a knob: the operator dials `bolt+ssc` (TLS, unverified — verification would force pod-DNS SANs and a CA onto a user-facing cert and buys nothing while Bolt is unauthenticated; Bolt auth is the trigger to revisit) and falls back to the other scheme once, because a roll turning TLS on or off leaves coordinators in the old mode while the spec says the new one (`memgraph.dialSchemes`); the ServiceMonitor switches to https with `insecureSkipVerify`. Probes are TCP and untouched. Rotation is not the operator's: the Secret is mounted without `subPath` so the kubelet refreshes it, and Memgraph picks it up on `RELOAD BOLT SERVER TLS` until the core reloads by mtime (planned upstream); the operator watches no Secret and never restarts for an in-place update, and a `secretName` change is an ordinary roll. `intraCluster` (`secretName`; `tls.crt`/`tls.key`/`ca.crt` mounted read-only at `/etc/memgraph/intra_cluster_tls`, the three `--cluster-*-file` flags always together) is mTLS proving membership, not identity: Memgraph verifies the chain and demands a client cert but checks no hostname, so one shared cert is the shape (nine of thirteen surveyed operators do the same). Its presence is pinned by a CEL transition rule on `MemgraphClusterSpec`, not on `TLSSpec`, because a rule on the block does not fire when the block is added or removed whole: a member with it cannot talk to one without, so a one-pod-at-a-time roll deadlocks on lag. `secretName` changes roll normally; a CA cut-over needs a bundled `ca.crt` in both Secrets, documented, not detected. Renewal is `RELOAD INTRA_CLUSTER TLS` per instance until the core reloads by mtime (Raft already does).
- **Scheduling** (`spec.scheduling`) restates the HA chart's `affinity` block in the shape the survey of sixteen operators converged on (CloudNativePG's): one rule the operator writes, `podAntiAffinity` (`type: preferred | required`, `scope: role | cluster`, `topologyKey`), presence-based like every other optional block, so an absent block writes no rule at all and `{}` is the chart's soft per-role default; plus per role the raw `core/v1` surface (`nodeSelector`, `tolerations`, `topologySpreadConstraints`, `podAntiAffinity`, `priorityClassName`) passed through as written. The chart's `parity` is `required`/`role`, its `unique` is `required`/`cluster`, its `nodeSelection` is a per-role `nodeSelector`. Two builder conveniences: a spread constraint naming no `labelSelector` gets the role's selector, and role anti-affinity terms are *appended* to the operator's rule list by list, never merged or replacing it. Nothing is pinned and the controller does nothing new: a change is a pod-template change the roll carries. The CRD's compact JSON must stay under the 256KB client-side apply limit; the `core/v1` schemas here cost about 47KB of it.
- **Monitoring** (`spec.monitoring`) is OpenMetrics only, and the endpoint is unconditional: both roles declare a `metrics` port on 9091 (container and headless Service) and pin `--metrics-port=9091 --metrics-format=OpenMetrics`, because Memgraph's enterprise build serves it regardless and a user-owned ServiceMonitor/PodMonitor must work with an empty spec. The block only creates objects for a stack the user runs, each presence-based like `externalAccess` (no `enabled`, no `namespace`: owner references cannot cross namespaces, and Prometheus Operator's `serviceMonitorNamespaceSelector` covers it). `serviceMonitor` (`labels`, `annotations`, `interval`) builds one typed ServiceMonitor from the `prometheus-operator/.../pkg/apis/monitoring` module, selecting both headless Services by identity labels on port `metrics`; the external Services carry no such port and yield no targets. The CRD is never bundled: `main.go` discovers it once at start (`controller.ServiceMonitorServed`), the kind is owned and listed only if served, and a cluster asking for it without gets `Converged=False/ApplyFailed`. Monitoring objects carry the `memgraph.com/monitoring` marker and are pruned by it through the shared `pruneKind`, separately from the external-access marker. The module ships no CRD, so `test/crds/` carries the ServiceMonitor CRD YAML at the module's version: envtest loads it, `hack/kind-prometheus-crds.sh` applies it in the e2e Kind cluster, and no Prometheus runs in the suite. The endpoint's `scheme` follows `spec.tls.bolt` (https with `insecureSkipVerify` when set), never a knob. `grafanaDashboard` (`labels`, default `grafana_dashboard: "1"` and a named set *replaces* it; `annotations` for `grafana_folder`) builds one ConfigMap `<cluster>-grafana-dashboard` holding the HA chart's `memgraph_openmetrics.json`, `go:embed`ded from `internal/resources/dashboards/` and updated by copying the chart's file over it; it is applied every pass like everything else (no skip-if-unchanged path), and the ConfigMap informer is label-scoped in `main.go` like the Pod one because every namespace has ConfigMaps. `vmagentRemote` (the HA chart's block, and how Memgraph monitors customer clusters: the customer's cluster pushes metrics outbound to the VictoriaMetrics Memgraph runs, since Memgraph cannot scrape into their network; `remoteWrite.url` required, `remoteWrite.basicAuth.secretName`, `scrapeInterval` default `15s`, `externalLabels` CEL-checked as Prometheus label names, `image.{repository,tag,pullPolicy}`, `resources`; no `enabled`, `namespace`, `httpPort` or key-name knobs) runs one vmagent Deployment `<cluster>-vmagent` plus a ConfigMap `<cluster>-vmagent-config` holding a `scrape.yml` rendered by marshalling a typed struct (`internal/resources/vmagent.go`): one job `memgraph` with static pod-DNS targets on 9091 at the **applied** counts (so `desiredMonitoring` takes `replicaCounts`), scheme following `spec.tls.bolt`, re-read by vmagent through `-promscrape.configCheckInterval=1m` so a scale changes no pod. The basic-auth Secret has fixed `kubernetes.io/basic-auth` keys, feeds `-remoteWrite.basicAuth.username=$(VMAGENT_BASIC_AUTH_USERNAME)` from an env var and `-remoteWrite.basicAuth.passwordFile` from a read-only mount (re-read every second, never on the command line; the pinned image has no `usernameFile`); the operator still holds no Secret RBAC. The pod runs as uid 65534 under `restrictedSecurityContext()` with no ServiceAccount token because the image names no user; the chart's `kubernetes.*` infra-scraping branch is deliberately out (cluster-scoped RBAC no owner reference collects). Deployments joined the RBAC markers, `Owns`, the label-scoped cache in `main.go` and `pruneMonitoring`. The e2e deploys a single-node VictoriaMetrics in the cluster namespace and asserts every instance's `up` series arrives with the external label. `vectorRemote` (the chart's block, the logs half of the same remote monitoring: `logsEndpoint` required, a base URL Vector appends `/loki/api/v1/push` to; `auth.secretName` with the same fixed keys, both reaching Vector as env vars it interpolates with `${LOGS_USERNAME}`/`${LOGS_PASSWORD}`; `extraLabels`; `image`; `resources`; no per-role switches, `websocketPort`, `namespace` or logs-dashboard ConfigMap) adds a `vector` sidecar after the uploader and before user containers on **both** roles (`internal/resources/vector.go`, hooked in `podContainers`/`podVolumes`) on one shared ConfigMap `<cluster>-vector-config` (`vector.yaml` marshalled from a typed struct; per-pod values come through env: `ROLE`, downward-API `POD_NAME`/`POD_NAMESPACE`). Source is Vector's `websocket` on `ws://127.0.0.1:7444`, Memgraph's always-on monitoring websocket (both roles, no off switch, streams `{"event":"log","level":…,"message":…}` with only quotes and newlines escaped, so the VRL remap keeps unparseable frames whole with `level=unknown`; `warning`→`warn`, `critical`→`fatal` like the chart); with `tls.bolt` it is `wss` with `tls.enabled: true` and verification off, because the websocket shares the Bolt TLS context and Vector does not infer TLS from the scheme (smoke-tested). Loki sink labels are the chart's (`app`/`job` memgraph, `role`, `namespace`, `pod`, `level`) plus `extraLabels`, `healthcheck` off, `remove_label_fields`. Vector retries a refused websocket itself, so it may start before Memgraph listens; the sidecar has no probe. Adding/removing the block is a roll; the e2e deploys a single-node VictoriaLogs, watches the roll in and out, and asserts every pod's lines arrive via LogsQL `stats by (pod)`.
